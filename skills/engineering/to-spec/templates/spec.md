# Spec 模板（派发时必须全文传递）

> 以下标题和顺序必须原样保留在 issue 正文中。各节说明用于约束内容，编写最终 spec 时应替换为项目的具体需求，不要留下占位文字。

## 问题陈述

用户正面临的问题，从用户的角度描述。说明现有流程的障碍、受影响用户以及为什么需要解决。

## 解决方案

问题的解决方案，从用户的角度描述。描述用户完成任务时将获得的能力、可观察的行为和预期效果。

## 用户故事

提供一个**极其详尽**、连续编号的用户故事列表，覆盖该功能的方方面面，包括适用的主流程、异常场景、权限、边界情形以及与现有功能的交互。

每条必须使用以下格式：

1. 作为一个<角色>，我想要<功能>，以便<收益>

示例：

1. 作为手机银行客户，我想看到我账户的余额，以便能对消费做出更明智的决定

## 实现决策

列出已作出的实现决策。可以包括：

- 将要构建或修改的模块
- 将被修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

准确区分**已确认决策**与**基于现有代码库推导的待确认假设**。遵循相关 ADR 和项目领域术语。

**不得写具体文件路径或普通代码片段**，因为这些细节可能很快过时。

唯一例外：如果原型产出了比散文更精确地编码某个决策的状态机、reducer、schema 或类型形态，可内联决策密集的精简片段，并注明其来自原型；不是可运行演示。

## 测试决策

列出已作出的测试决策，包括：

- 什么构成好的测试：只验证外部可观察行为，不测试实现细节
- 哪些模块或用户行为将被测试
- 测试接缝：优先复用已有接缝，在尽可能高的层级测试，尽量减少新接缝，理想情况下一个
- 代码库中类似测试的先例
- 需要覆盖的关键成功、失败和边界场景
- 测试接缝是否已经用户确认；未确认的必须明确标记为“建议接缝（待用户确认）”

## 范围外

描述本 spec 范围之外的内容。区分明确排除事项与尚未讨论、因而不可擅自纳入范围的事项。

## 补充说明

记录关于该功能的补充说明，如相关 ADR、依赖、兼容性要求、技术风险，以及未解决但不阻止本次 spec 发布的问题。
