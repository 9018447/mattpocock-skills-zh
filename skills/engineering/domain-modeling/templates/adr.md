# ADR 模板（派发时必须全文传递）

ADR 存放在所属 context 的 `docs/adr/`，单 context 项目默认使用根目录 `docs/adr/`。首次确实需要 ADR 时再创建目录。遵守项目已有约定和 ADR。

## 标准模板

```md
# {决策的简短标题}

{1 到 3 句话：上下文是什么，做了什么决定，以及为什么。}
```

最短可只有一段。重点是“已经作出的决定及原因”，不是填充章节。

## 只有三项全部成立才建 ADR

1. **难以逆转**：事后改主意的成本高。
2. **脱离上下文令人困惑**：以后读代码的人会问为什么不选常见替代。
3. **真实权衡**：存在可行替代方案，选择有明确理由。

没全部通过就跳过 ADR，不要把每次选择都记为 ADR。

常见合格事项包括：架构形态、contexts 的集成方式、具有锁定效应的技术选型、清楚的范围与所有权边界、有意偏离惯例的路径、代码不可见的强约束，以及值得以后记住的替代方案否决理由。

## 文件命名与编号

按所属 `docs/adr/` 目录的已有最大编号加一，使用 `0001-slug.md`、`0002-slug.md` 等形式；不得复用已有编号。只在决定确实需要落盘时创建文件。

## 可选内容

仅在增添真实价值时使用：

- `Status` frontmatter：`proposed`、`accepted`、`deprecated`、`superseded by ADR-NNNN`
- `Considered Options`：被否决的替代方案值得记住时
- `Consequences`：有非显而易见的后续影响时

默认不加这些章节。原则是决定清晰、原因可追溯、文字简短。
